# Análise de Segurança — Rooster One

Avaliação item a item, classificada como Implementado / Parcial / Não identificado / Recomendação. Referências completas em `01`–`04` desta pasta.

| Item | Status | Nota |
|---|---|---|
| Autenticação por token | Implementado | JWT, guard global, reverifica usuário ativo no banco a cada requisição. |
| Expiração de sessão | Implementado | Access token de 8h, renovável por refresh token de 30 dias (`POST /auth/refresh`), com rotação a cada uso: a sessão antiga é sempre revogada, então um token vazado e usado faz o legítimo falhar em seguida, em vez de os dois conviverem. O banco guarda só o hash SHA-256. `POST /auth/logout` revoga. A renovação revalida `usuario.ativo`, então desativar alguém encerra o acesso sem esperar as 8h. |
| Hash de senha | Implementado | bcryptjs, 10 salt rounds. |
| Redefinição de senha segura | Implementado | Token de uso único, hash SHA-256, expira em 1h, resposta anti-enumeração. |
| Autorização granular (RBAC) | Implementado | Direto por usuário, checada em guard global + em alguns controllers para regra de dono do recurso. |
| Proteção contra SQL Injection | Implementado | Nenhum SQL bruto; Prisma parametriza por padrão. |
| Validação de entrada | Implementado | `ValidationPipe` global com whitelist. |
| CORS restrito a produção | **Não implementado** | Configuração atual aceita qualquer porta localhost — não é apropriada para produção com domínio fixo. |
| Rate limiting em login | Implementado | `@nestjs/throttler`, `ThrottlerGuard` global (120 req/min por IP, `src/auth/auth.module.ts`) + `@Throttle()` mais rígido nas rotas sensíveis: 8/min em `/auth/login`/`/auth/esqueci-senha`/`/auth/redefinir-senha`/`POST /boost/login`, 5/min em `POST /boost/cadastro` (`src/auth/throttle.util.ts`). Os limites relaxam automaticamente quando `NODE_ENV=test` (Jest define isso sozinho) — senão o e2e, que faz dezenas de login na mesma janela, ficaria flaky por `429` em vez de testar o que devia. |
| Headers de segurança HTTP | Implementado | `helmet()` em `main.ts` — CSP desligado deliberadamente só pra não quebrar o Swagger UI (`/api/docs`, que usa script/style inline); os demais headers do Helmet (HSTS, X-Frame-Options, X-Content-Type-Options, etc.) ficam ativos em toda rota. |
| Validação de tipo de arquivo em upload | **Corrigido** | Era um achado real: só o tamanho era limitado, qualquer mimetype passava. `criarFiltroMimetype`/`MIMETYPES_DOCUMENTO` (`src/common/storage.config.ts`) validam anexo de chamado, documento acadêmico, entrega do Learn e material de apoio do Boost (pdf/office/imagem/texto/zip); o vídeo do Boost tem allowlist própria (`MIMETYPES_VIDEO`, mp4/webm/mov). Testado em e2e (upload com mimetype fora da lista recebe `400`). |
| Criptografia de arquivo em repouso | **Implementado (setembro/2026)** | Antes todo arquivo gravado em disco (anexo de chamado, documento acadêmico, anexo de entrega, material/vídeo do Boost, certificado, nota fiscal) ficava em texto puro em `uploads/` — legível por qualquer um com acesso ao disco, backup ou um servidor de arquivo estático mal configurado. `src/common/file-encryption.util.ts`: documentos (tudo, exceto vídeo) em AES-256-GCM (autenticado — arquivo adulterado falha ao decifrar, em vez de servir lixo); o vídeo hospedado do Boost (até 2GB, único que usa HTTP `Range` para a barra de progresso) em AES-256-CTR, sem tag de autenticidade mas com decifragem de um trecho arbitrário sem processar o arquivo inteiro. Chave mestra única (`FILE_ENCRYPTION_KEY`, 32 bytes, obrigatória — aplicação recusa subir sem ela, mesma disciplina do `JWT_SECRET`), IV aleatório por arquivo. **Trade-off aceito conscientemente**: o esquema de vídeo (CTR) não detecta adulteração do arquivo cifrado no disco — ameaça mais estreita (exige acesso de escrita ao servidor) que a que isto resolve (leitura crua do disco). Arquivos já existentes antes desta mudança continuam em texto puro até serem reenviados — sem produção ainda, não há migração retroativa. Prova de ponta a ponta em e2e: lê o arquivo cru direto do disco (não pela API) e confirma que o conteúdo original não aparece nos bytes gravados. |
| Exposição de hash de senha na API | **Corrigido** | Era um achado real: `GET /usuarios`, `GET /usuarios/:id`, `POST/PATCH/DELETE /usuarios` (`usuarios.service.ts`) e as respostas de chamado com `usuario`/`tecnico` embutidos (`rooster-desk.service.ts`, 5 pontos) retornavam o objeto `Usuario` completo do Prisma, incluindo `senhaHash`, por não usarem `select`. Corrigido com uma constante `USUARIO_SAFE_SELECT` aplicada em toda consulta que devolve `Usuario`/`usuario`/`tecnico` nesses dois arquivos, mais um ponto equivalente encontrado e corrigido no próprio `rooster-finance/notafiscal.service.ts` (`GET /notas-fiscais` trazia `cobranca.aluno.usuario` completo). Confirmado ao vivo via curl (grep por `senhaHash` na resposta) e pela suíte e2e completa (35/35) sem regressão. |
| Dependências com vulnerabilidade conhecida | **Achado em aberto** | `npm run audit` (`npm audit --omit=dev`) em setembro/2026: frontend limpo; backend com **8 avisos** — `multer` (DoS por vazamento de descritor, bypass do limite de tamanho por corrida no `fileFilter`, DoS por índice de array em nome de campo), que entra via `@nestjs/platform-express`, e `qs` (bypass do limite de array, DoS). Confirmado por `npm audit fix --dry-run` que **não existe correção não-quebrante**: resolver exige subir `@nestjs/platform-express` para a major seguinte. Não aplicado aqui por ser mudança de raio amplo, que pede avaliação de impacto própria — segue como recomendação priorizada. |
| Senha mínima uniforme | **Corrigido** | Era um achado real: criação de usuário e cadastro do Boost exigiam 8 caracteres, mas `RedefinirSenhaDto` aceitava 6 — dava para contornar o mínimo usando o fluxo de "esqueci minha senha". Unificado em 8, com teste de regressão (`src/common/validacao-dtos.spec.ts`). Login não impõe mínimo de propósito: senha curta ali é credencial errada, não requisição malformada. |
| Validação de entrada com cobertura explícita | Implementado | Além do `ValidationPipe` global, há suíte dedicada verificando as restrições de DTO uma a uma (`validacao-dtos.spec.ts`) — antes cada regra era exercitada só indiretamente por algum caso e2e. |
| Acessibilidade auditada automaticamente | Implementado | axe-core sobre os componentes compartilhados (`acessibilidade.test.tsx`). Não substitui verificação manual de foco, teclado e leitor de tela. |
| Segredos fora do código-fonte | Implementado | `JWT_SECRET`/`DATABASE_URL` só por variável de ambiente, sem fallback. Desde setembro/2026 há `.env.example` nos dois repositórios (só com placeholders), e o `.gitignore` do frontend passou a ignorar `.env` — antes não ignorava, então um arquivo de ambiente ali seria versionado. |
| Proteção do último administrador | **Corrigido** | Era um achado real (riscos R-01/R-04): os três caminhos que levavam a perder o último administrador — revogar a permissão, excluir o usuário, desativá-lo — não tinham nenhuma trava, e o resultado era irreversível pela interface, já que não sobrava ninguém capaz de conceder a permissão de volta. Agora os três respondem `409` (`shared/administradores.service.ts`, RN035), contando apenas administradores **ativos**, porque usuário inativo não autentica. Coberto por teste e2e nos três caminhos, incluindo o caso em que a trava "anda" para o novo último administrador. |
| Logs não expõem senha/token em texto puro | **Corrigido** | Era um achado real: o log de e-mail em modo dev (sem SMTP) gravava o **link de redefinição de senha completo**, com o token em texto puro — e, se um ambiente de produção subisse sem `SMTP_HOST` por engano, passaria a despejar o token de redefinição de qualquer usuário no log do servidor. Agora: (1) em produção, o fallback é tratado como erro de configuração — o log registra a falha e **nada do conteúdo** é escrito; (2) fora de produção, o link é gravado com `mascararSegredosNaUrl`, que troca o valor de `token`/`senha`/`password`/`secret`/`key` por `***`, preservando o resto da URL. O token completo continua acessível pelo `outbox` em memória, usado pelos testes. Coberto por teste unitário (`mail.service.spec.ts`). |
| Auditoria de eventos de segurança | Implementado | Login, CRUD de usuário, concessão/revogação de permissão e redefinição de senha gravados automaticamente. |
| IDOR / path traversal armazenado em anexo de chamado | **Corrigido (pentest interno, setembro/2026)** | Era um achado real, encontrado por teste ativo contra o servidor: `CreateAnexoTicketDto` aceitava um campo `caminho` livre do cliente, gravado sem validação por `RoosterDeskService.create()` (helper CRUD genérico) e depois usado para montar o caminho real de download. Qualquer usuário com a permissão comum `anexar` podia criar um `AnexoTicket` apontando `caminho` para o arquivo de **outro** anexo já existente no sistema — inclusive de um ticket ao qual não tinha acesso — e baixá-lo através de um ticket próprio. Corrigido removendo `caminho`/`tipo`/`tamanho` de `CreateAnexoTicketDto` (e de `UpdateAnexoTicketDto`, que o herda); com `ValidationPipe({forbidNonWhitelisted:true})` já global, isso basta para a requisição ser recusada com `400`. Confirmado que nenhum outro módulo tem um DTO equivalente. Coberto por teste de regressão e2e. Detalhe completo, com todos os testes ativos realizados (JWT, injeção, elevação de privilégio, rate limiting, etc.) em `docs/security/06-pentest-2026-09.md`. |
| Validação de tipo de arquivo por conteúdo real (magic bytes) | **Achado em aberto (baixo risco)** | `criarFiltroMimetype` valida só o `Content-Type` declarado pelo cliente na parte multipart, não o conteúdo real do arquivo — confirmado ativamente: um executável (assinatura `MZ`) foi aceito como `image/png`. Risco considerado baixo porque `Content-Disposition: attachment` (todo endpoint de download) e `X-Content-Type-Options: nosniff` (Helmet) impedem o cenário mais perigoso — execução inline no navegador — e `image/svg+xml` já está fora da allowlist. Ver `docs/security/06-pentest-2026-09.md` e `docs/engineering/10-melhorias-futuras.md`. |

## Recomendações priorizadas

1. Restringir CORS a domínio(s) fixo(s) antes de qualquer deploy fora de ambiente local.
2. Atualizar `multer`/`@nestjs/platform-express` para a versão sem os avisos conhecidos (é breaking change — avaliar impacto antes).
3. Validar o conteúdo real (magic bytes) do arquivo enviado, não só o `Content-Type` declarado pelo cliente — risco baixo, já mitigado por `Content-Disposition: attachment` + `nosniff` (ver tabela acima).
4. Restringir ou remover o Swagger (`/api/docs`) antes de um deploy em produção — hoje público sem autenticação, apropriado só para desenvolvimento (achado do pentest interno, `06-pentest-2026-09.md`).
