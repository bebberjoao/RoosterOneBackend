# Migrations — Rooster One

Histórico incremental de `prisma/migrations/` (15 migrations), cada uma como uma pasta `<timestamp>_<descricao>/migration.sql`. O provider registrado em `migration_lock.toml` é `postgresql` — todas as migrations foram escritas e aplicadas contra PostgreSQL.

## Comandos do projeto (`package.json`)

| Script npm | Comando real | Uso |
|---|---|---|
| `npm run prisma:migrate` | `prisma migrate dev` | Desenvolvimento: cria e aplica uma nova migration a partir do diff do `schema.prisma`, gera o client. |
| `npm run prisma:deploy` | `prisma migrate deploy` | Produção/CI: aplica as migrations pendentes já existentes em `prisma/migrations/`, sem gerar novas nem pedir confirmação interativa. |
| `npm run prisma:generate` | `prisma generate` | Gera o Prisma Client a partir do `schema.prisma` (Postgres). |
| `npm run db:seed:dev` | `ts-node prisma/seed-dev.ts` | Popula um banco de desenvolvimento com dados de exemplo (ver `06-seeds.md`). |
| `npm run prisma:generate:test` | `prisma generate --schema ./prisma/schema.test.prisma` | Gera o client de teste (SQLite), usado por `test:e2e`. |
| `npm run prisma:db:push:test` | `prisma db push --schema ./prisma/schema.test.prisma` | Sincroniza o schema de teste direto no SQLite sem gerar arquivos de migration (usado só nos testes e2e). |

## Observação histórica importante

O schema atual **não tem** conceito de Perfil/Role — mas o banco já teve um. As migrations 1, 4 e 10 mostram a evolução completa: o modelo original (`usuario → perfil → permissao`, com tabelas `perfis`, `usuarios_perfis`, `perfis_permissoes`) foi introduzido na primeira migration e depois desmontado na migration 10 (`20260916125542_usuarios_permissoes`), migrando os dados para a ligação direta atual `UsuarioPermissao`. Isso é relevante para quem lê apenas o `schema.prisma` de hoje: ele reflete o estado final (sem Perfil), mas o histórico de migrations preserva o motivo da mudança nos comentários do próprio SQL.
